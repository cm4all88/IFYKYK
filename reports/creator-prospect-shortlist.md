# Creator prospect shortlist

**Triaged:** 2026-07-26 · **Reviewed:** 100 prospects · **PRIORITY:** 15 · **BACKUP:** 10 · **REJECTED:** 75 · **Contacted:** 0

Every prospect was scored on the rubric you set — niche fit 20, recent activity 20,
verified business contact 20, existing monetization 20, independent/self-managed 10,
profile quality 10.

Two things shaped the outcome more than anything else.

**Contact is the binding constraint.** Only 33 of the 100 publish a verifiable business
contact method, and both PRIORITY and BACKUP require one. So the 25 shortlisted names were
drawn from a pool of 33, and the other 67 were rejected on that ground alone — not because
anything about them failed verification.

**Recency is a gate, not a score.** PRIORITY requires "recently active", so a prospect whose
newest evidence is stale cannot buy its way in on monetization or contact strength. Three
creators scoring 85–87 sit in BACKUP for exactly this reason: **Emma Rea (87)**, **Hendri
Vermeer (86)** and **Mo's Parlor (86)** all outscore two of the PRIORITY entries, but none
publishes a date. That is the gate working as specified.

## Using this in the admin console

`creator_prospects` has no `priority` or `status` column and none was added, so the classes
ride on the existing `stage` column that `app/admin/prospects/page.tsx` already filters on:

| Class | `stage` | In the admin filter |
|---|---|---|
| PRIORITY | `qualified` | **Select "Qualified" to see exactly these 15**, ranked by score |
| BACKUP | `identified` | Select "Identified" |
| REJECT | `disqualified` | Select "Disqualified"; each carries a `disqualified_reason` |

`data/creator-prospects-seed.sql` carries the triage. It also contains a commented-out UPDATE
block to use instead if the rows were already imported before triage, since `ON CONFLICT DO
NOTHING` would otherwise skip them and leave the old stages in place.
